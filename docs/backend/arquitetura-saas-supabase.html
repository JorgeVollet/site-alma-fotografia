A virada

De demonstração para sistema real

Hoje o painel é lindo, mas funciona com dados de "faz de conta" guardados no navegador. Agora vamos construir o backend de verdade: um banco de dados na nuvem, login real da equipe, e armazenamento das fotos. Tudo que já existe e tudo que vem por aí passa a funcionar para valer.

O princípio que guia tudo: trocar a fonte dos dados, não reescrever as telas. Os módulos que você já viu (Funil, Seleções, Clientes…) continuam exatamente iguais por fora — só que por baixo deixam de ler o "faz de conta" e passam a ler o banco real.

3 decisões que fazem essa arquitetura valer ouro

1
Pensado como produto que se clona. Cada estúdio tem o seu próprio banco de dados (Supabase), totalmente isolado. A Alma tem o dela; o próximo cliente terá outro projeto separado. Para vender para outro fotógrafo, você só clona a estrutura num banco novo e vazio — cada cliente paga o próprio Supabase, e você não carrega o custo de todos num lugar só. Isolamento total: cada estúdio é uma ilha.
2
O código fica muito mais limpo. Toda aquela complexidade de "dados de demonstração que não podiam mudar" simplesmente desaparece. Com banco real, editar um cliente é só… editar o cliente. É a maior simplificação do projeto.
3
Segurança de verdade. Cada estúdio só enxerga os seus próprios dados, garantido pelo banco (não por confiança no navegador). As chaves secretas nunca saem do servidor. É o padrão de um sistema profissional.

As 6 melhorias, já contempladas

Tudo que você pontuou com o dono da Alma já está desenhado dentro da arquitetura — cada uma com seu lugar no banco e na ordem de construção.

1
Prazos por etapa de produção. Cada ensaio ganha sub-etapas (edição → tratamento de cor → retoque de pele), cada uma com seu próprio prazo, responsável e lembrete. Acaba o "prazo único de 15 dias" sem controle do que acontece dentro dele.
2
Valor de foto extra por cliente. Na hora de enviar as fotos pra seleção, o estúdio define o valor da foto extra daquele ensaio (porque negociam caso a caso). Se não definir, usa o valor padrão do pacote.
3
Kanban estilo Trello. Um quadro de produção com colunas que o estúdio cria e renomeia, e cards arrastáveis — substituindo o Trello que usam hoje, dentro do próprio sistema.
4
Seleção de fotos mais rica. O cliente seleciona clicando na própria foto (não só no coração), amplia com um toque, e pode deixar uma observação por foto ("arrumar o cabelo", "tirar a mancha") que o editor lê na hora de tratar.
5
Aniversários. Data de nascimento no cadastro + alerta dos aniversariantes do mês na tela inicial (ordenados pelo mais próximo) + relatório completo. Acaba a venda perdida por não saber que o cliente fazia aniversário. (Mensagem automática via WhatsApp com modelos prontos fica para a fase seguinte.)
6
Mais relatórios. Hoje só existe o do funil. Entram relatórios de aniversariantes, financeiro e produção — todos com filtros.

Segurança & acesso

Login real e proteção dos dados

Como a equipe entra, e como o banco de cada estúdio fica protegido — equipe de um lado, cliente final do outro.

Login da equipe

O Maurício, a Aline e a equipe entram no painel com e-mail e senha de verdade (Supabase Auth), substituindo o "admin123" de demonstração. Cada pessoa tem um papel (admin, fotógrafo, editor, atendimento) que define o que pode ver e fazer.

Cada estúdio é uma ilha

Como cada estúdio tem o seu próprio banco de dados, o isolamento é físico e total — não há como um estúdio acessar dados de outro, porque eles são bancos completamente separados. Dentro do banco de cada estúdio, uma trava de segurança (RLS) ainda protege o que é interno da equipe do que o cliente final pode acessar.

O acesso do cliente final

O cliente da Alma não precisa criar conta. Ele entra na galeria dele com o código de acesso + senha (como já é hoje), e o sistema valida isso no servidor com segurança. Ele vê só as fotos dele, seleciona, deixa observações e baixa as finais quando liberadas. As fotos originais em alta nunca ficam expostas.

A regra de ouro: a chave secreta do sistema nunca vai para o site (que qualquer um pode inspecionar). Ela fica só no servidor. O que protege os dados de verdade é a trava do banco. Por isso, antes de colocar qualquer dado real, toda tabela é blindada.

Onde cada coisa acontece

Aqui comigo × no Claude Code

Backend de verdade pede o terminal para algumas coisas (rodar o banco, configurar chaves, testar login). A divisão inteligente:

TarefaAqui (planejar/gerar)Claude Code (executar)
Estrutura do banco e segurançaGero os arquivos prontosVocê aplica no Supabase
Código das telas conectando ao bancoEscrevo tudoRoda e testa ao vivo
Criar o projeto Supabase + chavesPasso o passo a passoVocê faz no painel Supabase
Testar login, upload, segurança—Só dá pra validar ao vivo
Resumindo: eu preparo toda a arquitetura, os arquivos do banco e o código aqui — você (ou a gente junto) executa a conexão e os testes no Claude Code. É a mesma divisão que combinamos para a Nota Fiscal.
